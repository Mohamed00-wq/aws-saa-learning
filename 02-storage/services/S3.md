# S3 — Simple Storage Service

## What it is

S3 (Simple Storage Service) is AWS's object storage service. It stores data as **objects** in **buckets** — there is no file system, no hierarchy of folders, and no OS. Data is stored redundantly across multiple availability zones and is accessible over HTTP/HTTPS via a REST API, the console, the CLI, or SDKs.

S3 is the backbone of virtually every AWS architecture. If EC2 is where code runs and DynamoDB is where structured data lives, S3 is where **files and data at rest** live — backups, static assets, data lakes, media, logs, and application state. It is nearly always the answer for storing files, and it underpins many other AWS services (CloudFront origins, Athena queries, EMR data, backups, etc.).

## Key concepts

### Buckets

A **bucket** is a container for objects. Bucket names are **globally unique** across all AWS accounts and regions (not just your account). Bucket-level properties include:

- **Name** — globally unique, 3–63 characters, lowercase letters, numbers, hyphens, periods.
- **Region** — where the bucket is physically stored. Data is stored in the region you pick; you can access it from anywhere, but it physically resides in one region.
- **Versioning** — when enabled, keeps multiple versions of the same object (including deleted-marker versions) so you can recover from accidental deletion or overwrite.
- **Access control** — bucket policies, ACLs, and block public access settings.

Note: a bucket **cannot** be renamed once created. To change the name, create a new bucket and copy the data over.

### Objects

An **object** is a single piece of data — any file type (image, video, JSON, CSV, database backup). Objects have:

- **Key** — the full path to the object (e.g. `images/profile.jpg`). The key is not a folder but a "virtual path" — S3 has no real directories. Prefixes (`images/`) are just part of the key name. Max key length is 1024 bytes.
- **Value** — the actual content (up to 5 TB per object).
- **Metadata** — system metadata (size, ETag, last-modified) and user-defined metadata.
- **Version ID** — present only if versioning is enabled.

**Object size limits:** a single object can be up to **5 TB**. The **PUT** API handles uploads up to **5 GB** in a single call. For larger objects, you must use **Multipart Upload**, which splits the file into parts (each up to 5 GB, minimum 5 MB per part except the last) and uploads them in parallel.

### Storage Classes

S3 offers multiple storage classes, each with different cost, retrieval time, and durability:

| Class | Use case | Retrieval |
|---|---|---|
| **S3 Standard** | Frequently accessed data, low latency | Instant |
| **S3 Intelligent-Tiering** | Unknown/varying access patterns; auto-moves data between tiers by access | Instant (no retrieval fee) |
| **S3 Standard-IA** (Infrequent Access) | Infrequently accessed but needs fast retrieval | Instant (per-GB retrieval fee) |
| **S3 One Zone-IA** | Infrequently accessed data that can be recreated; single AZ (no multi-AZ resilience) | Instant |
| **S3 Glacier Instant Retrieval** | Archived but rarely accessed; millisecond retrieval | Instant |
| **S3 Glacier Flexible Retrieval** | Archive data; minutes to hours retrieval | Minutes to hours |
| **S3 Glacier Deep Archive** | Long-term archive; lowest cost | 12–48 hours |

**Lower cost = slower retrieval and/or lower resilience.** The durability is 99.999999999% (11 nines) for almost all classes (One Zone-IA and Reduced Redundancy are less).

### Lifecycle Rules

You can configure **lifecycle rules** to automatically transition objects between storage classes and expire (delete) them based on age:

- **Transition actions** — move objects to IA or Glacier after N days (e.g. "move to Standard-IA after 30 days, Glacier after 90 days").
- **Expiration actions** — delete objects after a set time, or delete old versions.
- **Minimum age rules** — objects must be at least 30 days old before you can transition them to Standard-IA/One Zone-IA, and 90 days before transitioning to Glacier. You cannot transition directly from a write to Glacier on day 1.

Lifecycle is a key cost-optimization tool and a very common exam topic.

### Encryption

S3 encryption is applied at rest and controlled via the **default encryption** setting of a bucket:

- **SSE-S3** — server-side encryption managed by S3 (AES-256). Zero configuration, no key management.
- **SSE-KMS** — encryption using a **KMS key** you manage. Adds an API call and you control key rotation and who can decrypt.
- **SSE-C** — you provide and manage your own encryption keys. S3 uses the key for encryption but discards it; you must provide the key with every request.
- **Client-side encryption** — you encrypt data before uploading it; S3 never sees plaintext.

**On the exam:** SSE-S3 is the default and simplest; SSE-KMS is used when you need to control/audit key access; SSE-C when you must hold your own keys.

### Access Control

S3 access control has several layers:

- **IAM policies** — identity-based; control which users/roles can access which buckets/objects.
- **Bucket policies** — resource-based; attached to the bucket. Can grant cross-account access (specify a principal from another account). This is how you make buckets public or share them with other accounts.
- **ACLs** — legacy object/bucket-level access lists; generally avoid in favor of bucket policies.
- **Block Public Access** — a bucket/account-level setting that blocks public access. Even if a bucket policy grants public access, Block Public Access can override it. This is a strong exam point.

**Best practice:** use IAM for principals in your account, bucket policies for public or cross-account access, and keep Block Public Access on by default.

### Static Website Hosting

S3 can host **static websites** (HTML, CSS, JS, images) with no web server:

- Enable **Static website hosting** on the bucket.
- Provide an **index document** (e.g. `index.html`) and optional **error document**.
- Bucket policy must allow public read (`s3:GetObject`).
- You get a URL like `http://<bucket-name>.s3-website-<region>.amazonaws.com`.

S3 websites do **not** support HTTPS natively (the S3 website endpoint). To serve HTTPS, put **CloudFront** in front (recommended) or use a custom domain with a certificate.

Note: this is a distinct endpoint from the REST API endpoint (`s3.<region>.amazonaws.com/<bucket>`).

### Versioning

When **versioning** is enabled on a bucket, each object gets a **version ID**. Every upload, overwrite, or delete creates a new version:

- Uploading the same key creates a new version (previous version preserved).
- Deleting an object creates a **delete marker** — the object is "removed" from view but the delete marker and all prior versions are retained.
- You can recover deleted data by removing the delete marker or restoring a prior version.
- Versioning is a defense against accidental deletion and overwriting, and is often combined with lifecycle rules (expire old versions) to control storage costs.
- Versioning cannot be turned off once enabled (only suspended).
- MFA Delete can be enabled to require MFA for permanent deletion of versions.

## Architecture deep dive

### Consistency model

S3 provides **strong read-after-write consistency** for both PUT and DELETE operations of objects and listings. After a successful write or delete, any subsequent request will see the latest data — there is no eventual consistency window for updates or deletes as there was with older versions of S3. This simplifies app design.

### S3 ↔ EC2 relationship

- **AMI storage:** AMIs are stored in S3 (the underlying snapshot data). Launching an EC2 instance reads the AMI from S3.
- **Application data:** instances can read/write files directly to S3 over HTTPS (via SDK or CLI), or mount S3 as a POSIX-like filesystem using **Mountpoint for Amazon S3**.
- **Bootstrapping:** user data scripts and configuration assets are often fetched from S3 at instance boot.
- **Starving I/O-bound workloads:** moving shared files from local EBS disks to S3 decouples instances from each other.

**Key contrast:** EBS is block storage attached to a single EC2 instance; S3 is object storage accessible from anywhere over HTTP. EBS supports low-latency random reads (databases); S3 is for durable shared file storage.

### S3 ↔ CloudFront relationship

**CloudFront is a CDN** that serves content from edge locations and **uses S3 as its origin**. Benefits:

- **Lower latency** to end users (cached at the edge).
- **HTTPS** served natively (unlike the plain S3 website endpoint).
- **DDoS protection** via AWS Shield.
- **Cost savings** on repeated downloads (edge caching reduces S3 GET requests).
- Can **restrict access to the S3 bucket** using an **Origin Access Control (OAC)**, so users can only reach content via CloudFront, not directly via S3.

**On the exam:** "users download large static content globally" → CloudFront in front of S3. "S3 website needs HTTPS" → CloudFront + custom domain + ACM cert.

### Multipart Upload

For large files (>100 MB, required above 5 GB) **Multipart Upload** is used:

- Uploads the object in parallel parts.
- Resumes from failed parts (retry only the failed part, not the whole file).
- Enables pausing/resuming and predictable upload time for large media.
- The minimum part size is 5 MB (except the last part); max part is 5 GB.

Multipart is also used implicitly by the AWS CLI and SDKs for large transfers and by **S3 Transfer Acceleration** workflows.

### S3 Transfer Acceleration

**Transfer Acceleration** (Amazon CloudFront edge locations) speeds up uploads over long distances by routing traffic through the nearest AWS edge location over the optimized AWS backbone network, instead of the public internet. You use an accelerated endpoint: `<bucket>.s3-accelerate.amazonaws.com`.

Use when: large files, geographically distant clients, slow/fluctuating public networks. Not needed for small objects or regionally co-located clients.

### Event notifications & S3 to Lambda

S3 can emit **event notifications** on object events (Put, Post, Copy, Delete) to:

- **Lambda** — trigger serverless processing (thumbnail generation, validation, ETL).
- **SQS** — queue the event for a worker to process.
- **SNS** — publish notifications.
- **EventBridge** — route events to other AWS services (more advanced filtering and routing).

This makes S3 a natural event-driven ingress point for data pipelines.

### Security options summary

| Concern | Solution |
|---|---|
| Encrypt data at rest | SSE-S3, SSE-KMS, SSE-C, client-side |
| Encrypt in transit | HTTPS / TLS (SSL endpoint) |
| Control who can access | IAM policies, bucket policies, ACLs |
| Prevent accidental public exposure | Block Public Access |
| Audit access | CloudTrail / S3 server access logging |
| Object-level confidentiality | S3 Object Lock (WORM), presigned URLs for time-limited access |
| Malware/file-type checks | GuardDuty (Malware Protection for S3), Macie (sensitive data) |

**Presigned URLs** grant temporary, time-limited access to a private object without making the bucket public — e.g. "allow this user to download this file for the next 15 minutes."

## Advanced gotchas & edge cases

1. **Bucket names are globally unique.** Two accounts (or regions) can never share a bucket name. This trips people up when they copy bucket names across environments.

2. **Multipart upload minimums.** Single PUT max is 5 GB; objects can be up to 5 TB via multipart. Parts must be ≥5 MB (except the last).

3. **Deleting a versioned object creates a delete marker, not removal.** The data is still billed until you permanently delete the versions. Watch out for ever-growing versioning storage costs.

4. **Lifecycle minimum ages.** You cannot transition an object to Standard-IA/One Zone-IA before 30 days, or to Glacier before 90 days. Exam questions often test this.

5. **Glacier Deep Archive retrieval takes 12–48 hours.** If a question needs "fast" retrieval, choose Standard, IA, or Glacier Instant — not Deep Archive.

6. **S3 website endpoint is HTTP only.** The default S3 website URL does not support HTTPS. Use CloudFront + ACM certificate, or the REST endpoint with TLS.

7. **Block Public Access is a safety net.** Even if a policy allows public access, Block Public Access (account-level) overrides it. This is a common contrast with bucket policies.

8. **Bucket policies are required for cross-account access.** IAM in your own account works for internal users, but granting another AWS account access requires a bucket policy (resource-based).

9. **Read-after-write consistency is now strong.** S3 guarantees strong consistency for PUT, DELETE, and listing. No more eventual-consistency gotchas for new objects.

10. **Storage class ≠ durability for all.** One Zone-IA and the (legacy) Reduced Redundancy classes do NOT give 11 nines durability — the data is in a single AZ.
